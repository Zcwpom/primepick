# 支付与订单链路改造方案

> 起因：感觉「支付页太简单，项目不敢上线」。
> 结论先说：**简单不是问题，自相矛盾才是问题。** 支付不可能接真实网关（需要企业资质），
> 所有作品集项目都是模拟支付 —— 面试官看的不是「你有没有接支付宝」，而是
> **「每条路径点下去有没有结果、状态前后是否一致、边界有没有处理」**。

> **进度**：**P0 止血已完成** —— 端到端冒烟从 5 项扩到 **12 项全绿**（含「支付后订单状态变为待发货」），
> 并新增支付页 / 支付结果页截图。过程中又抓到 2 个 bug（`skuId` 契约错误、`unref(getter)` 陷阱），
> 详见文末「P0 完成记录」。P1（真实感）与 P2（亮点）待做。

---

## 一、先回答「能不能上线」

| 维度 | 结论 |
| --- | --- |
| 技术上能不能部署 | **能**。mock 层已让站点自给自足，不依赖任何后端 |
| 现在该不该上线 | **先别**。现在上线等于把下面 8 个断点直接摆在面试官面前 |
| 判据是什么 | 不是「支付真不真」，而是**任何按钮点下去都有明确反馈，且数据前后一致** |

**最致命的一条**（面试官点两下就能撞到）：

```
订单列表「立即付款」→ /pay?id=xxx → 支付页显示一张跟这单无关的静态二维码
                                    → 点「支付成功」→ 跳回首页
                                    → 回到订单列表，订单**仍然显示待付款**
```

用户刚「付过款」，订单还是待付款，购物车也没清 —— 这是**数据自相矛盾**，比「页面简陋」严重得多。

## 三、修改方案

### P0 · 止血：让链路自洽（约 2~3 小时）

目标：**任何一个按钮点下去都有明确结果，且前后数据一致。**

1. **支付页接订单**：读 `route.query.id` → `getOrderAPI(id)` → 展示订单号 / 下单时间 / 应付金额 / 商品缩略图 / 收货人
2. **二维码与订单绑定**：用订单号生成二维码（见第四节依赖取舍），不再用静态图
3. **「我已完成支付」真的走流程**：
   `POST /member/order/:id/pay` → 成功后 `router.replace('/paycallback?orderId=xx&payResult=true')`
   → 支付结果页展示金额与状态，提供「查看订单」「继续购物」
4. **修订单列表时间显示**：用 `payLatestTime` + `useCountDown` 渲染 `mm:ss`；已过期显示「已超时」（顺手让第 8 条死代码复活）
5. **修我引入的 mock 字段 bug**：订单 sku 改为「以 fixture 首个 sku 为模板 + 覆盖已知字段」，保证字段与真实契约完全一致（`realPay` / `skuId` / `attrsText` 全齐）
6. **mock 补 3 个接口**（它们同时就是方案 B 后端的路由契约）：
   - `POST /member/order/:id/pay` → `orderState: 2`（待发货）
   - `POST /member/order/:id/cancel` → `orderState: 6`（已取消）
   - `POST /member/order/:id/receive` → `orderState: 4`（待评价）
7. **扩冒烟脚本**：加一条「创建订单 → 支付 → 订单列表状态变为待发货」的断言，堵住第 6 条那种盲区

### P1 · 真实感：像真的支付流程（约半天~1 天）

1. **倒计时归零 → 订单超时关闭**：自动切「订单已超时」态，提供「重新下单」；mock 侧按 `payLatestTime` 判定
2. **支付结果轮询**：2s 一次、带退避、最多 N 次；过程中显示「支付结果确认中」；超时给出明确文案而不是假装成功
3. **支付方式切换**：支付宝 / 微信 + 支付渠道（PC / 移动），与 Checkout 的 `payType` / `payChannel` 字段打通
4. **失败与取消路径**：取消 → `orderState=6`；重复点击**幂等**（同一订单并发点击只发一次请求）
5. **订单列表按钮真的能用**：取消订单 / 确认收货 → 调接口 + 刷新列表（把 8 处「开发中」清到 0~2 处）
6. **空态与异常态**：订单不存在 / 已支付 / 已超时 / 网络失败，各自有明确页面

### P2 · 亮点：能讲出设计取舍（约 1 天）

1. **订单状态机**：把合法迁移写成纯函数（`canPay(order)` / `canCancel(order)` / `nextState(order, action)`）+ 单测；
   非法迁移（如已取消的订单去支付）在前端就被挡住
2. **为什么支付不能乐观更新**：不可逆操作必须有 `pending / success / failed` 三态；
   对比「购物车可以乐观更新」——**知道边界在哪，比会写代码更值钱**，这是面试里最能讲的一段
3. **跨标签同步**：支付成功后 `BroadcastChannel` 通知其它标签页刷新订单状态
4. **漏斗埋点**：创建订单 → 调起支付 → 支付成功，记录各步耗时与流失率
5. **幂等设计**：前端请求合并 + 幂等键，解释「为什么支付接口必须幂等」

## 四、依赖取舍：要不要引入 `qrcode`

| 方案 | 评价 |
| --- | --- |
| 引入 `qrcode`（约 20 kB gzip） | ✅ **推荐**。API 简单，能生成含订单号的真实二维码 |
| 手写二维码编码器 | ❌ 这是 Reed-Solomon 纠错编码，造这个轮子不加分，只会引入 bug |
| 继续用静态图 | ❌ 就是当前的问题本身 |

**关键**：`qrcode` 只在支付页需要 → 用**动态 `import()`** 加载，正好复用现有的路由懒加载，
不污染首屏预算（`npm run size` 会盯着）。

### 过程中新抓到的 3 个 bug

1. **真实契约里没有 `skuId`**：订单项的字段是 `{ id, spuId, name, quantity, image, realPay, curPrice, totalMoney, properties, attrsText }`，
   而订单列表用 `item.skuId` 拼「查看详情」链接 → 一直跳 `/detail/undefined`。已改用 `spuId`。
2. **`useCountDown` 里 `unref(getter)` 的经典陷阱**：最常用的传法是 getter 函数（`() => order.payLatestTime`），
   而 `unref` 只解包 Ref、**不会调用函数** → 拿到函数源码字符串 → `Invalid Date` → 倒计时恒为 0
   → 支付按钮永远不出现。**这个 bug 是被冒烟测试抓出来的**：断言失败时脚本打印了「实际落在哪个页面」，
   看到标题和订单信息都对、只差按钮，直接锁定到 `payable` 为 false。

> 这条正好印证了第 5 节的验证方式：DOM 冒烟不是形式主义 —— 第 2 个 bug 靠类型检查、lint、构建**都发现不了**。

3. **商品详情页缺 `brand` 字段就整页空白**（录 GIF 时才暴露）：
   `goods-1369155859933827074` 这份**真实响应里没有 `brand`**，而模板直接写 `goods.brand.name`
   → 渲染期抛 TypeError → 整个内容区空白。面包屑也写死了 `categories[0]` / `categories[1]` 下标。
   已改为 `goods.brand?.name || '暂无品牌'` + 由 `categories` 推导面包屑。
   **这类「字段缺失」是真实数据的常态**，一个点进去白页的商品足以毁掉整场演示。
   冒烟脚本已补上对应断言：`无 brand 字段的商品详情页正常渲染（面包屑 4 项）`。

> 3 个 bug 里有两个（第 2、3 个）是**只有真的把页面跑起来**才会暴露的 —— 这也是为什么这一轮的
> 验证不是「跑个 lint + build」就收工。

## 八、P1 完成记录：真实感

**状态：已完成** —— 端到端冒烟从 13 项扩到 **17 项全绿**。

| # | P1 项 | 落地情况 |
| --- | --- | --- |
| 1 | 倒计时归零 → 超时关单 | **关单是服务端职责**：mock 在读取订单时清扫过期待付款单（`sweepExpiredOrders`），前端倒计时归零后重新拉一次订单，自然进入「订单已关闭」态 —— 而不是前端自己变个提示、刷新又变回待付款 |
| 2 | 支付结果轮询 | `pollOrderPaid()`：首次等 0.8s（给网关回调留时间）→ 最多 5 次、线性退避；期间按钮显示「正在确认支付结果…」；超时未确认时提示「支付结果确认中，请稍后到我的订单查看」，**不假装成功** |
| 3 | 支付方式/渠道贯通 | 支付页选的渠道随 `POST /member/order/:id/pay { payChannel }` 提交并写回订单，**支付结果页按 `payChannel` 回显**「支付宝 / 微信支付」；另外补了 `payType=2`（货到付款）的分支：不展示二维码，直接说明无需在线支付 |
| 4 | 取消订单 / 确认收货 | 都走真接口 + `ElMessageBox` 二次确认；用 `acting` 表做**幂等保护**（连点两下只发一次请求，key 为 `订单id:动作`），按钮带 loading |
| 5 | 清理「功能开发中」 | **全项目 0 处**。商品详情页移除「查看评价 / 收藏商品 / 品牌主页 / 服务详情」4 个只弹提示的假入口（同步删掉对应死 CSS）；订单列表移除「查看物流 / 评价商品 / 查看评价 / 申请售后」；登录页移除「短信登录」占位 tab 与死 CSS |
| 6 | 空态 / 异常态 | 支付页四态齐备：可支付 / 已支付 / **货到付款** / **已超时或已关闭**；订单不存在走 `el-empty` 并给「查看我的订单」引导 |

### 一个刻意的「不做」

**「再次购买」被移除了，不是忘了做**：订单详情接口返回的订单项字段是
`{ id, spuId, name, quantity, image, realPay, curPrice, totalMoney, properties, attrsText }` ——
**没有 `skuId`**，而加购接口必须传 `skuId`。也就是说在不改后端契约的前提下，
前端无法可靠地「再次购买」（一个 spu 可能有多个 sku，猜不得）。

> 这个观察本身就值得在面试里讲：**「前端做不了」有时候不是能力问题，是契约缺字段**，
> 正确做法是提需求补字段（订单项带上 skuId），而不是在前端硬凑一个能跑的假实现。

### 新增断言（冒烟 17 项）

```
[OK]   支付渠道贯通到订单（payChannel=2）
[OK]   取消订单后状态为已取消（orderState=6）

```

## 九、P2 完成记录：能讲出设计

### 1. 订单状态机抽成纯函数（+ 23 个单测）

新增 `src/domain/order-state.js`：把「哪些状态迁移合法」收敛成一张表，

```js
const TRANSITIONS = {
  pay:     { from: [UNPAID],      to: UNDELIVERED },
  cancel:  { from: [UNPAID],      to: CANCELLED   },
  receive: { from: [UNRECEIVED],  to: UNCOMMENTED },
}
```

对外只暴露 `canPay / canCancel / canReceive / nextState / orderStateText`，
页面里不再出现 `order.orderState === 1` 这类散落的判断（支付页、订单列表都改成调用它）。

**为什么值得抽**：原先状态规则散在多个页面，加一个状态要改好几处，而且没人能一眼说清
「哪些迁移是合法的」；抽成纯函数之后可以直接单测 —— 不需要起组件、不需要连后端。

顺带接入了 **Vitest**（项目此前一个测试都没有），CI 增加 `test` job：

```
✓ src/domain/order-state.test.js      (15 tests)
✓ src/components/XtxSku/power-set.test.js (5 tests)
✓ src/composables/useCountDown.test.js    (3 tests)
Tests  23 passed (23)
```

测试写出来就抓到了两个东西：

- **幂集的组合爆炸有据可查**：`2^n` —— 10 个规格维度 1024 个子集、20 个维度 104 万。
  这条断言让「为什么要重构 SKU 算法」从感觉变成了数字。
- **服务端秒级精度 vs 前端毫秒精度**：`payLatestTime` 只有秒精度，而 `Date.now()` 有毫秒，
  `floor((deadline - now)/1000)` 会少 1 秒（89 而不是 90）。测试基线必须对齐到整秒，
  这个差异是写测试时才暴露出来的。

### 2. 取舍说明：为什么支付**不能**乐观更新

| | 购物车 | 支付 |
| --- | --- | --- |
| 操作性质 | 可逆（再点一次就改回来了） | **不可逆**（钱已经出去了） |
| 结果来源 | 前端自己就能算出来 | 由**支付网关异步回调后端**决定 |
| UI 策略 | 可以乐观更新：先改界面，失败再回滚 | 必须悲观：`pending → 轮询确认 → success/failed` |
| 失败代价 | 用户看到数字跳回去，再点一次 | 用户以为付成功了，实际没付（或反之）→ 投诉 / 资损 |

所以 `pollOrderPaid()` 在查清楚之前一直保持「正在确认支付结果…」，
查不到就明确说「支付结果确认中，请稍后到我的订单查看」，**绝不假装成功**。
这段取舍是这一轮最值得在面试里讲的内容：**知道哪里不能用乐观更新，比会用乐观更新更值钱。**

### 3. 跨标签同步

`src/utils/crossTab.js`：支付成功 / 取消订单后广播 `order:changed`，
其它标签页的订单列表收到后刷新。优先 `BroadcastChannel`，
不支持时退回 `localStorage` + `storage` 事件；卸载时务必解除监听（否则泄漏）。

> 为什么不用 `storage` 一把梭：`BroadcastChannel` 不把消息回传给发送者本身，
> 天然没有自触发循环；`storage` 只是老浏览器的兜底。

### 4. 支付漏斗埋点

`src/utils/analytics.js`：记录 `order_created → pay_submitted → pay_confirmed / pay_failed`，
可算出各步到达次数、相邻转化率，以及**单笔订单「下单 → 支付确认」的耗时**
（支付结果页会把耗时显示出来：「支付耗时：1.2 秒」）。

**刻意不做假的网络上报**：事件只进内存环形缓冲 + 开发环境打印（`window.__primepickAnalytics` 可查），
因为演示项目没有收集端，硬造一个上报接口反而更可疑；接真实上报只需替换 `report()`。

### 5. 顺带清理

- 订单列表里重复的状态文案映射表删除（改用 `orderStateText()`）
- `formatPayState` 这个拼错的函数名随之消失

### 6. 冒烟脚本升级成「走真实 UI 下单」

原先冒烟是用 `fetch` 直接建单的，这带来了两个盲区：
埋点里的 `order_created` 永远不会被记录（只有结算页会发），
而且**结算页「提交订单」这条最重要的路径其实没被测到**。

改成在结算页点「提交订单」之后，顺带暴露了一个真实约束：
**走 UI 是 SPA 路由跳转（不刷新页面），内存里的埋点事件才不会丢**。
如果测试里用 `Page.navigate` 做整页跳转，事件会被清空，支付耗时断言必然失败 ——
这条约束和真实用户路径完全一致，所以测试是**更可信**了，而不是被放宽了。
